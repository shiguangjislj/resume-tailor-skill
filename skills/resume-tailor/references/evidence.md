# 证据与表达规则

## 事实状态

- 用户明确陈述：可以据此改写，注明内部来源；不等同于第三方独立验证。
- 材料记载：保留出处及日期；简历里已有的强成果仍可能需要澄清。
- 待确认：不能用确定语气写入投递稿；可以降低措辞或暂时省略。
- 分析推测：只能作为建议或问题，不能当成个人经历。
- 已更正：留存变更说明以防旧稿恢复，正文只使用最新确认口径。

数字记录：对象、周期、样本/分母、基线、结果、来源、估算与否、个人/团队归属。并非所有指标都需要所有字段，但改善率与因果结论需要更完整证据。

数量证明范围；采用证明落地；效率/质量变化证明局部改善；业务指标证明相应业务表现。外部明确确认也可作结果。不要把任一层自动升级到另一层。

## 常见逻辑纠正

| 原表述风险 | 应如何处理 |
|---|---|
| 看板上线就等于数据驱动决策 | 问清什么数据改变了什么行动；否则写数据采集与复盘支持 |
| 对比两个模型就叫A/B测试 | 先写横向对比；有明确实验设计证据再使用A/B术语 |
| 品牌商单Brief直接产生评分标准 | Brief对齐商业需求；评测通常从目标用户、场景、成功标准及验证目标拆解 |
| 应用失败就是底层模型能力差 | 区分输入、提示词、工具链、环境、配置和模型等可能原因，只写验证到的层级 |
| 提交问题即完成改进闭环 | 反馈是动作；修复闭环需有处理、复测及验证结果 |
| 小样本案例即完整评测体系 | 先写评测方案/案例；体系化需有复用标准、流程及实际执行依据 |
| 定时采集等于实时追踪 | 按真实采集频率写，不改变时效性 |
| 几个Skill等于数据意识/效率提升 | 写覆盖流程与采用情况，改善效果另找证据 |
| 提示词模板等于可执行Skill | 核对是否有可调用指令、任务流程和资源；按实际形态命名 |
| 文章阅读量证明产品转化或模型质量 | 只能直接证明传播表现；转化、质量需各自证据 |
| 团队结果全部归个人 | 交代个人职责和贡献，不把团队规模写成个人增量 |
| 方法论“可复用于所有场景” | 写已形成的资产与实际复用；潜在迁移作为面试讨论 |
| 临时补做算进实习成果 | 按实际日期写个人项目或后续迭代 |

“用户需求”也要有来源：访谈、评论、社群、历史数据或业务观察，区分直接反馈与推测。不要强行把有限样本称为完整用户画像或代表整个市场。

## 面试可追问，但不无限深挖

一项强主张至少能解释实际对象、个人行动和证据。简历阶段只解决会影响写法的缺口；更深的技术原理、失败案例和方法论放进面试准备清单。

需要学习时写明：当前事实缺口/概念误用 → 为什么影响判断 → 学习重点 → 如何用一个小实践验证。学习建议放在正文外，不能把学习完成前的计划写成经验。

## 隐私与发布

公开包使用全新虚构组织和数字，不仅替换真实姓名。禁止将本地上下文、联系方式、源简历、账号数据、内部截图或访问令牌混入公开仓库。发布前检查实际待发布文件列表和内容；`.gitignore`不是已经跟踪文件的保护措施。
