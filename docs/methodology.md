# 方法改进与推导逻辑

以下是针对编辑质量和减少返工的设计假设，不是对招聘成功率的保证。

| 原有方法的不足 | 推导逻辑 | Skill中的改进 | 代价/边界 |
|---|---|---|---|
| 用户每补充一点就增加正文 | 信息完整与岗位相关是不同目标；新增信息会挤占高价值证据的篇幅 | 素材库保留全部，简历通过岗位能力映射后筛选 | 素材库需要维护，不能假定跨会话记忆 |
| 用同一份“产品能力”模板投不同岗位 | 同名岗位可能负责应用、评测、平台或增长；泛化标签无法解释具体匹配 | 先提炼JD核心能力，再分配3—4个模块 | 无JD时只能做方向版，不能伪称精准匹配 |
| 每条必须有数字 | 数量只能证明范围，不能自动证明质量、因果或数据能力 | 区分交付、采用、效率质量、业务效果、外部确认 | 无效果数据时允许真实但较弱的产出证据 |
| 用完整流程或“闭环”代替深度 | 多个步骤不代表有反馈改变下一轮决策；流程长也可能只是执行多 | 保留关键判断及验证；仅写实际完成到的阶段 | 简历省略的步骤放入面试素材 |
| 直接把用户口述改为专业术语 | 口述可能混淆A/B、横向对比、模型与应用、模板与Skill | 事实优先，术语校正，待确认项留在正文外 | 有时需要短追问，但不无限访谈 |
| 一条反馈引发整篇重写 | 不受影响的内容也变化，会制造新的事实冲突和偏好回退 | 最新用户稿为基准，局部修改，保留接受/否决记录 | 目标岗位变化仍可能需要整体重选材 |
| 方法论只写“可迁移” | 潜在适用不是已经验证的复用价值 | 写真实资产、采用者和复用；迁移假设单列 | 不为了显得高级编造团队采用 |
| Skill里直接存个人经历 | 通用方法要公开，个人素材需要保密且常更新 | 公共包与本地上下文物理分离 | 换环境需迁移素材，不会自动同步 |
| 只检查文件结构就称“验证通过” | SKILL.md合法不意味着模型会做正确选择 | 结构校验、机械脚本测试、行为用例审查分开报告 | 独立模型实测未做时明确写未完成 |

## 使用阶段对应的完成标准

- 访谈阶段：已找到改变简历写法的关键事实，不要求把所有面试知识提前学完。
- 方向适配：每个重点模块能对应岗位能力，不能通过包装消除真实资格缺口。
- 正文改写：每项主张有依据、个人边界清楚、字数和段数合适。
- 导出阶段：文本可复制、排版可读、关键内容未截断，链接可用。
- 后续迭代：修改源于新的事实、岗位或明确反馈；达到上述标准后停止无依据润色。

## 还可以怎样提高方法质量

收集真实使用中的可观察结果：事实修正次数、反复询问已知信息次数、超出篇幅次数、用户接受前的修改轮数。比较同类任务，避免把岗位热度和候选人背景差异导致的面试率变化归因给Skill。先从减少返工与事实错误验证价值，再讨论更远的求职效果。
